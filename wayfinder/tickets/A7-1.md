## Question

Prefill 阶段（全量 S 个 token 并行）和 Decode 阶段（逐 token 自回归）的 C 提取策略解耦：

候选：
- **(S) 同样算法**：Prefill 和 Decode 用同一提取算子（实现简单但 decode 必须满足 budget）
- **(D) 不同算法**：Prefill 用全精度算法（如 truncated SVD），Decode 用近似算法（如 EMA 增量）
- **(A) Prefill only**：Decode 阶段直接复用 Prefill 算出的 C（不重算）

**关键问题**：
- Decode 算力预算 1 token 等价多少 FLOPs？
- C 是否需要每层重算还是可以层间共享？

## Resolution

**锁定：(S) 同样算法 + 零分支实现**

### 算子范式

| 维度 | Prefill (S>1) | Decode (S=1) |
|---|---|---|
| **算法** | `(L')` 投影 + 双重球面归一化 | `(L')` 投影 + 双重球面归一化（**零分支**） |
| **张量流转** | `[B, S, H_kv, d_k] → [B, S, d_c]` | `[B, 1, H_kv, d_k] → [B, 1, d_c]` |
| **物理存储** | 临时显存（Backward 需保留梯图） | SRAM / Registers（随用随弃，零 HBM 读写） |
| **路由 Logit** | `logit_i = β(C_t^T c_i - 1)` | `logit_i = β(C_t^T c_i - 1)` |
| **KV Cache 接口** | **禁用 C 存入** | **禁用 C 读写** |

### 零分支原则

- 代码层面 **无 Prefill/Decode 分支**
- batch 维度自动 broadcast（PyTorch 原生支持）
- 同一 kernel / op / autograd graph

### 复杂度

| 阶段 | 算力 | 存储 |
|---|---|---|
| Prefill | `O(B · S · d_c · d_k)` (并行) | `[B, S, d_c]` for backward |
| Decode | `O(B · 1 · d_c · d_k)` (sequential) | `[B, 1, d_c]` SRAM-only |

### KV Cache 接口约束

- **C 禁入 KV Cache**——两边都禁用
- KV Cache 只存 K, V（A2-1 Post-FFN 替换标准约定）
- C 是 per-token 即时计算的，不跨 step 复用

### 物理存储介质

- **Prefill**：C 存 HBM 显存（Backward 需要保留梯图）
- **Decode**：C 走 SRAM/Registers（16-dim 太小，无需 HBM 读写）
  - 16 floats = 64 bytes，远小于 SRAM 容量
  - 计算完 logit 后立即用，下个 token 重新算（无跨 step 状态）

### 后续 ticket 影响

- A7-2 (增量更新律)：因 C 不缓存，"增量更新"无对象——A7-2 实际是 **(R) 直接重算**的论证
- A7-3 (硬件友好度)：Decode 走 SRAM/Registers 意味着 C 是 latency-friendly 的；Custom kernel 需求低
- A8-1 (Baseline)：所有 baseline 同样禁 C 缓存

### Future Work

- **Prefill 阶段 SVD 精提 ablation**：离线分析时可用，推理不走
- **C 缓存到 KV Cache**：如果 latency 要求极致，可考虑（但 16 floats / token 额外存储）
- **C 跨层共享**：相邻层 C 可能冗余，可考虑 layer-wise C 共享（spec 复杂）
