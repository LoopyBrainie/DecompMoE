# Design

## Context

三条坐标必须先分清，否则整份台账会锚在错误的位置上：

1. **审计的 pin 态**——`.audit/**` 里的行号、`基线: unchanged-since-pin` 等字段全部指向一个更早的 commit（`6593a06`）。
2. **当前 HEAD** = `8ba7d6f`（2026-10-02 19:19 由并行 session 推进；本 change 的门禁 0.1 初次落盘时是 `f6461d7`，两者之间的提交只改了一个归档 change 的 `design.md`，未触及 `src/` / `tests/` / `openspec/specs/`，故全部实测结论不变）。
3. **Change 2 的成果**——`sphere.py` / `tests/test_sphere.py` / 三份 spec **已在 HEAD 提交**，不是「只在工作树」。真正 untracked 的是它的**归档目录**，以及本 change 自己的 `evidence/`。

即两端并不对称，但不对称的真实范围远小于原先设想：工作树承载的只有 `src/decompmoe/gating.py`（F6 死防御删除）与 `wayfinder/tickets/WF-1.md`，**二者都不在求积测量链上**。这决定了 D4：第三方在 HEAD 重测会复现本台账，而不是审计的修前数字。

**注意漂移向量已换形**：原先的漂移源是「修复未提交」；现在修复已提交，漂移源变成「HEAD 会被并行 session 推进」。台账因此必须记录**生成时的 HEAD**，而不是「当时的最新状态」。

### 源文件的四层结构（分母口径）

`.audit/wayfinder-opsx-code-review/lists/opsx-changes.md` 里的 `###` 标题共 **135** 个，但**不是 135 条发现**：

| 层 | 数量 | 是否进入 108 分母 |
|---|---|---|
| `### AC-` / `### UD-` 发现 | **108** | 是 |
| `###` 章节标题（前言 / 交叉核查 / 盲区 / 勘误 / Dedup 等） | **27** | 否 |
| ├ 其中「盲区」小节 | 6 | 否 |
| └ 其中勘误相关小节（生效勘误 / 已撤回 / 复现命令 / E1–E19 / E20 / 根命题复核等） | 12 | 否 |
| 「盲区 1」登记的**无实体上游 finding** | **9** | 否（但见 D9，本 change 纳入） |

分节标题声明的条数与实际 `AC-`/`UD-` 标题数**逐桶相等**（24/15/15/15/18/7/8/6 = 108），108 无缺口——但这个结论的正确表述是「与 `AC-`/`UD-` 标题数相等」，不是「与 `###` 标题数相等」。原文写的是后者，推理错误：说「135 == 108」是荒谬的，说「108 个 `AC-`/`UD-` == 108」才成立。

已实测的实际分布：A-1 = 24、A-2 = 15、A-3 = 15、A-4 = 15、A-5 = 18、A-6 = 7、A-7 = 8、A-8 = 6（`### UD-01`…`UD-06`）。入范围 A-1..A-5 + A-7 = **95 条**（源内），加 9 条无实体 finding（见 D9）= **台账 104 条**。

## Goals / Non-Goals

**Goals:**

- 为 104 条（95 条源内 + 9 条无实体）各产出**一条可复算的依赖性判定**，附推导。
- 依赖者重测 + 重判 verdict；非依赖者记录「为何不依赖」。
- A-4 的行号指针按当前 HEAD 重算，不沿用 pin 态。
- 台账自洽：分母、桶归属、条目 id 全部与源文件实际内容对齐。

**Non-Goals:**

- ❌ 不修复任何一条发现——修复属于各自的 follow-up change。
- ❌ 不改 `src/**`、`tests/**`、`openspec/specs/**`、`wayfinder/**`、`.audit/**`。
- ❌ 不重跑审计本身（变异测试、覆盖率统计），只重测**数值与坐标**。
- ❌ 不为「凑完整」而对 A-6 / A-8 下的条目作判定。

## Decisions

### D1 — 依赖性判据是三段推导，不是关键词命中

每条判定必须写出：**① finding 依赖的具体量 → ② 该量的计算链是否经过 `_betainc_regularized` / `canonical_voronoi_angle` / 球面求积路径 → ③ 链上具体哪一行**。三者缺一不算判定完成。

**为什么**：本轮已三次证明关键词/字面量扫描产出的是与事实相反的「发现」——`e-01[23]` 计数、anchor 计数（多算 38 与少算 26 两个方向都错过）、以及把 `.audit` 里的 anchor 交叉引用当成 anchor 元素。字面量扫描还会系统性漏掉「用测试名或 spec 行号引用、根本不带数字」的条目（如 AC-08 引用 `canonical_voronoi_angle` 却不写数值）。

**备选**：字面量扫描（已证伪）；只查 `openspec/specs/` 正文（漏掉 src 侧与 test 侧）。

### D2 — 非依赖者也要写依据

「未纳入重测」必须写成「判定不依赖，理由是 X」，而不是留空。

**为什么**：留空的沉默省略与「判定后排除」在读者眼里无法区分，台账就会退化成一份看起来完整、实际有缺口的清单——这正是本仓反复出现的失效形态。

### D3 — verdict 分类法新增三个值，且全部由本 change 自行裁决

原审计词汇只有 `STILL_REAL` / `PARTIALLY_REAL` / `MOVED`，不足以表达本轮情形。新增：

| 值 | 含义 | 必附 |
|---|---|---|
| `RESOLVED_BY_UPSTREAM` | 缺陷的**成因**已被上游修复消除 | 因果链：原成因 → 上游哪处修复 → 为何消除。**不接受「现在测不到了」** |
| `DOWNGRADED` | 缺陷仍存在但性质/严重性变了 | 新旧严重性与新证据 |
| `REMEASURED_SAME` | 依赖成立、数值变了、verdict 不变 | 新旧数值对照 |

**本 change 认可的 verdict 全集恰为五个**：`STILL_REAL` / `PARTIALLY_REAL` / `RESOLVED_BY_UPSTREAM` / `DOWNGRADED` / `REMEASURED_SAME`。`evidence/tools/check_ledger.py` 的 `VERDICTS` 集合与本表逐项相等，两侧是同一个契约：

- **`MOVED` 不可用**。它是原审计对「坐标位移」的用词，本 change 的 D1 要求坐标类条目**重建**坐标而非承认位移，故须由本 change 用五值之一重新裁决；直接沿用 `MOVED` 会让检查器判 `not in [...]`。
- **`NOT_REAL` 不可用**。它曾出现在 `VERDICTS` 里而 D3 从未定义（审阅 finding，已修）——一个「检查器接受但设计从未批准」的值，正是决策链与执行层脱钩的形态。语义上「测出来不是真的」应按测得结果落 `RESOLVED_BY_UPSTREAM` / `DOWNGRADED`，并附因果链。

**为什么**：不新增 `RESOLVED_BY_UPSTREAM` 就会被迫把已消失的缺陷塞进 `PARTIALLY_REAL`，产出一条假的「部分仍成立」。

**纪律**：原清单的 `裁决` / `基线` 字段**一律不转抄**——本仓已实证这些字段本身会漂移（某桶 15 条里 4 条基线标错、5 条 `STILL_REAL` 已失效、1 条 Requirement 归错）。新裁决必须由本 change 用 `git show` / 实测得出。清单的**勘误节**（11 + 20 条）与本条同源，纪律相同但由 D8 单独成条，因为它还额外禁止「无锚点引用」。

### D4 — 两端分别锚定，并把这个不对称写进台账

- 审计侧坐标：`git show <pin-commit>:<path>`，绝不读 `.audit/` 里的行号字段。
- 新态侧：记录**当时的 HEAD commit + 工作树文件 sha256**，并对每个文件给出**内容级**判定（`IDENTICAL` / `CRLF_ONLY` / `CONTENT_DIFF`）而非仅字节级 sha256。

**为什么**：若只记 HEAD，第三方按台账重测会拿到修前实现，得到与台账相反的结果——这是最隐蔽的一种失效。

> **[2026-10-02 更正 · 0.1 实测推翻原假设]** 本决策原写「由于修复未提交，必须额外记录『基准由工作树承载』」。**该前提为假**：`sphere.py` 与 `tests/test_sphere.py` 在 HEAD 已含完整求积器修复（`_QUAD_RTOL=1e-12`、`_QUAD_MAX_PANELS=4096`、`t=sin²φ` 代换、`hi = π/2 − asin(√(1−x))` 抵消修复），且与工作树逐字节相同；3 份 spec 亦已在 HEAD，anchor **覆盖完整**（每条 Requirement 恰有一个独立 anchor、无重复）。绝对计数会随合法新增 Requirement 变动（wayfinder 在 `1afac58` 由 36 → 37），故契约检查的是覆盖而非常量。真正的坐标事实见上文 **Context 三条坐标**（工作树承载项只有 `gating.py` / `WF-1.md`，都不在求积测量链上），此处不重复叙述。
>
> 更正同时暴露一条**新的**基准纪律：工作树以 CRLF 存储而 HEAD blob 为 LF，朴素 sha256 比对会产出**若干**假阳性（`baseline.json` 的 `line_ending_caveat` 逐次列出当时的完整名单与 `head` 字段）。`git hash-object` 与 `git diff` 会归一行尾，裸哈希不会。**台账只准引用内容级判定**；`evidence/baseline.json` 现按 `IDENTICAL` / `CRLF_ONLY` / `CONTENT_DIFF` 三值落盘，并在生成脚本内置「M2/M3 必须与内容级判定一致」的断言。
>
> **[2026-10-02 二次更正 · 快照不是事实]** 原文把假阳性数量写死为「**6 个**（3 份 spec + `loss.py` + `safeguards.py` + `distance.py`）」，并据此在 R3 与 tasks 0.1 / 3.1 重复引用。实测该数字**不是一个仓库属性而是一次工作树快照**：随并行 session 提交先后测得 **6 → 10 → 9**。写死它有三个后果：(a) 后来者按「6」核对会得到「不符」而不知这是快照；(b) 「6」会被当成「CRLF 影响的文件数上限」这一**假平台限制**；(c) 它与同类的 anchor 计数病（写死 36/23/4）同源。**不变量是规则不是数字**：只准引用内容级判定。数量须与 `baseline.json` 的 `head` 字段一同引用。

### D5 — oracle 冻结并两路线互验

沿用 Change 0 的 `evidence/oracle.py`（dps=60，两条独立路线，5 个 `(N_e, d_c)` 上 `spread` 必须为 `0.00e+00`）。任何新数值先过 oracle，再与实现对账。

**为什么**：Change 0 的 oracle 首版自身有 label 反转 bug（`4.259e-07 < 1e-6` 被标成 FAIL）并把非判别点计入总判定。

### D6 — `.audit/` 不动，权威副本是本 change 的 `design.md`

沿用 Change 0 已裁决的策略。台账写在 change 目录，`.audit/**` 保持现状。

**补记**：`.audit/` 本身被 `.gitignore:37` 忽略、**从未进入版本控制**（`git ls-files` 对其报 `did not match any file(s) known to git`）。所以「只增不减」这一勘误节维护规则没有 git 历史兜底，本 change 的制品是这些结论**唯一可恢复的副本**——这抬高了 D10 的入库义务。

### D7 — 归档事故是**待验结论**，不是既定事实

**[2026-10-02 降级]** 本决策原把「archive 每份 spec 吞掉恰好 1 个 anchor、丢的是被改 Requirement 之后的那一个」写成既定事实。该结论来自 Change 2 的一轮观测，**尚未在独立条件下复现**；`tasks.md` 5.1 要求复现而非转抄。两者对同一事实的认知状态不一致，矛盾方向是「制品说得比证据多」。

现降级为**待验假设**，其内容与恢复源记录如下（作为 5.1 的复现目标，不作为 5.1 的输入）：

- 观测：每份被改 spec 各吞**恰好 1 个** anchor，且丢的是**被改 Requirement 之后的那一个**（`req-12` / `req-7` / `req-gov-2`）。
- 恢复源必须是 `git cat-file blob`——归档 delta 只能覆盖本 change 改过的那一块，而 wayfinder 丢的 `req-12` 并不在其中。
- AC-19 的原描述未涵盖「恰好一个」与「之后的那一个」，故 AC-19 需重判其**表述精度**，而非仅重判存活。
- **复现前，AC-19 / AC-20 / AC-80 一律不得据此判 `RESOLVED_BY_UPSTREAM`。**

### D8 — 勘误只作线索，不作依据

清单带两层既有裁决，本 change **一条都不引用为 verdict**：

- A-1 勘误节：**11 条生效**（E1 / E3 / E5–E13）、**2 条已撤回**（E2 / E4）。
- A-2 勘误节：**E1–E19 共 19 条 + E20**（E20 是 1 条勘误用 5 行观测表表达，按行数计会把勘误总数从 20 虚增到 24），**覆盖 A-2 全部 15 条**。

二者全部锚定 `188b9fb`、且测于求积器修复**之前**；当前 HEAD 是 `8ba7d6f`，其间有 5 个 commit 改过 `openspec/specs/`。故勘误的**坐标与数值均已过期**。

规则：

1. 勘误与盲区可用于**定位**（哪一行值得去看），**不得**作为 verdict 来源。
2. `verdict_evidence` 不得引用勘误的独特 token（修前字面量 `1.1735482746999482` / `1.0205068335735599` / `81.3148` 等）或勘误编号（`E1`…`E20`）**而无独立锚点**（`git show` / `git grep` / `@<rev>` / 复算 / 实测）。由 `check_ledger.py` 的 T5 强制。
3. 勘误正文自陈「**未重算任何数学**」（盲区 5），所有真值与误差量级原样取自上游、未复核——这加强而非削弱 D1。

> **反向注记（防止后来者抄走）**：A-2 勘误 E13 断言「6dp 字面量固有截断上界 `5e-7`，**任何 `< 1e-6` 的容差都会在真值上失败**」。该论断**已被证伪两次**：(a) 6dp **截断**误差恒 `< 1e-6`，`5e-7` 是四舍五入半单位而非截断界（反例 `trunc6(9.99999999) = 9.999999`，误差 `9.9e-7 > 5e-7`）；(b) 本仓 pytest **9.1.1** 的 `ApproxScalar.tolerance` 在 `rel is None and abs is not None` 时**直接返回 `abs`**，不进入 `max(rel·|expected|, abs)` 分支——`rel` 的默认值是 `None` 而非 `1e-6`，`DEFAULT_RELATIVE_TOLERANCE` 只在短路之后的分支里被引用。故 `abs=1e-6` 的实际容差**恰为 `1e-6`**，而截断误差 `4.259e-07 < 1e-6` ⇒ **不会失败**；实测把容差收紧到 `4.3e-7` 仍通过，E13「`1e-6` 是 6dp 显示格式允许的最小值」亦随之落空。裁决依据见 `evidence/tools/_pytest_approx_semantics.py`（读 pytest 源码 + 行为构造双证）。本 change 不引用 E13（见规则 1），此处登记是为了让这条已失效的论断有一个显式的死亡记录，而不是留作「可用的结论」。
>
> **注意同一错误论断的现存副本**（本 change 只判定不修复，登记待另开 change）：`openspec/specs/governance/spec.md` L13（义务 1，称 `abs=0` 时「`rel` 留在 pytest 默认 `1e-12`」→ 退化为 `1e-12·|expected|`）、L17（义务 3，称 `abs=1e-6` 的实际判据是 `max(1e-6, 1e-6·|expected|) = 1.17e-6`）、L22（同一 `max(...)` 判据）、以及 `tests/test_sphere.py:98-99` 的 docstring 副本。这四处须按本注记更正。**其判别力结论不受影响**：`1.275e-6` / `1.297e-6` 在 `abs=1e-6` 与 `max` 两种读法下都判 FAIL，`8.34e-7` 在两种读法下都判 PASS。

### D9 — 9 条无实体 finding 的 id、桶归属与坐标

「盲区 1」登记 9 条在 `classified.json` 里**完全没有实体**的上游 finding。它们**不是 `###` 标题**，而是 L1426–L1434 表格里的行。三个直接后果：

- **无 `ac_id`** → 用 `X-<上游 id>` 命名空间（`X-D1-02` / `X-D1-07` / `X-D2-02` / `X-D2-05` / `X-D3-01` / `X-main36` / `X-main38` / `X-main73` / `X-main78`）。不与 `AC-` / `UD-` 交叉，由检查器强制。
- **无桶归属** → 按缺陷性质分配：

| 桶 | 条目 | 依据 |
|---|---|---|
| A-1（→26） | `X-D1-02`、`X-D2-02` | 数值正确性无有效守卫 |
| A-2（→17） | `X-D1-07`、`X-D2-05` | spec 文本层缺陷 |
| A-3（→17） | `X-D3-01`、`X-main38` | spec ↔ src 语义偏离 |
| A-4（→18） | `X-main36`、`X-main73`、`X-main78` | 行号指针失效 |

  `X-D1-02` 归 A-1 而非 A-3 有争议（前者「无守卫」、后者「实现与 spec 偏离」），取 A-1 是因为它的规范表述就是「`Batch A` 首条、无测试守护」。
- **无 pin 坐标** → `provenance.source_ref` 指向盲区 1 的表格行；**D1 推导第③步的 `file:line` 必须从零建立**，不得借用任何勘误给出的行号。由检查器 T6 强制。

**为什么必须显式开这个口子**：`tasks.md` 7.2 原本的「ac_id 集合与源文件实际 `###` 标题逐字相等」断言，在加入 9 条后会永远报 9 条失配。若把它放宽成子集包含，例外就变得不可见。正确做法是**拆成两条独立判据**：95 条源内仍逐字相等（断言不放松），9 条 `X-` 另有一条可机器复核的判据。

**为什么值得纳入**：`X-D1-02` 正是本次求积器缺陷的**根因本体**（8 点 GL 单面板零细分、`b=1/2` 平方根奇点、MVP 工作点 67.24° 已越过 `x*=0.85`、89° 处相对误差 `1.1e-1`）。原 95 条范围里一条都不含——只重判症状、不判根因。

### D10 — 台账的唯一存放位置

- **机器可读主体**：`evidence/ledger.json`（schema 见 `tasks.md` 0.3）。所有判定写在这里，可被脚本 diff、可被检查器 gate。
- **`design.md`**：承载决策（本节）、逐桶小结、以及 7.3 的交付说明。不做 104 条的全量镜像——`ledger.json` 已 160 KB，逐条镜像会让 `design.md` 膨胀到不可维护。
- **`tasks.md`**：只承载执行顺序与验收条件。
- `proposal.md` 的 Impact 口径随之更正（原文写「逐条台账在 `design.md`」）。

### D11 — 证据必须入库，且不得用 `git add -A`

本 change 与它所重判的缺陷**同形**：`evidence/**`（7 个 JSON + 21 个工具）与 Change 2 的归档目录**全部 untracked**，而「change 目录未跟踪 / 制品完成却未入库」正是 AC-23 / AC-100 的主题。若本 change 带着未入库的证据归档，等于把被测缺陷再复制一份。

- 归档前必须把 `evidence/**` 与被重判的 Change 2 归档目录**入库**（`tasks.md` 7.4 强制）。
- **`git add -A` 会静默删除 4 个 HEAD 追踪但工作树已失的文件**：`2026-09-26-followup-spec-wording-bugs-after-precision-disclosure` 与 `fix-review-findings-voronoi-precision-and-lineage` 两个 change 的 `proposal.md` / `tasks.md`。任何提交前必须走选择性暂存，并以 `git status --porcelain` 复核。

## Risks / Trade-offs

- **[R1] 104 条的判定质量可能不均]** → 按桶分批交付，每桶交付前先跑一遍「三段推导是否齐全」的结构检查；缺项的条目留空并显式标记 `PENDING`，不得先勾后补。
- **[R2] 依赖性判定本身可能有争议]** → 判定必须定位到具体哪一行，争议可被定位到推导的某一步而非整体推翻。
- **[R3] 基准漂移使第三方无法重建台账]** → 台账同时记录 HEAD commit 与工作树 hash，且按 `IDENTICAL` / `CRLF_ONLY` / `CONTENT_DIFF` 三值给出**内容级**判定（D4）。**该风险已变形**：求积器修复已提交在 HEAD，工作树承载项（`gating.py` / `WF-1.md`）不在测量链上；但本轮实测中 HEAD 被并行 session 推进了 1 个 commit（`f6461d7` → `8ba7d6f`），证明「记录生成时的 HEAD」这一纪律不可省。CRLF 造成的字节级假阳性（数量随工作树变动，实测 6 → 10 → 9，见 D4 二次更正）也证明「只比字节」的锚定方式本身不可靠。
- **[R4] 把「缺陷消失」误判为「原 finding 本就错」]** → `RESOLVED_BY_UPSTREAM` 必须给出因果链；无因果链者一律降级为 `REMEASURED_SAME` 或保留原 verdict，不得判消失。
- **[R5] 依赖性判定把 A-4 的行号指针与 A-1/A-2 的数值问题混为一谈]** → A-4 的失效机制是**坐标位移**而非**数值失效**，台账须分列 `invalidation_kind: numeric | coordinate | provenance`，三类的重测动作不同。
- **[R6] 「不引用勘误」被架空成「不写 E 编号」]** → 真正的风险是把勘误的**结论**换个说法抄进去。D8 因此不只查 `E\d+` 编号，还查勘误独有的数值 token，并要求证据串自带独立锚点（T5）。
- **[R7] 9 条无坐标导致长期 `PENDING`** → 盲区 1 不提供 `file:line`，D1 第③步须从零建立。若某条建立不出坐标（如 `X-D3-01` 的 2001 点往返闭合测试需重新设计采样口径），该条**长期 `PENDING` 并写明缺什么**，不得借勘误补齐。
