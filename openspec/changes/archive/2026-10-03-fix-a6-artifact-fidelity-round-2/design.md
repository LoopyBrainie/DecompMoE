# Design

## D1 — review 的 F-1 被驳回，写入 design 以免重新提出

review 第一部分报 F-1（MEDIUM）：`opsx-changes.md:40` 与 `:110` 自述
「`23 条记 touched-since-pin、72 条记 unchanged-since-pin、13 条记 unverifiable`」，
而按 `### XX-NN` 条目块机械统计得 `23/74/12` = 109，判定自述与实测不符。

**本 change 独立复验后驳回。** 计数单位应当是 `基线:` **字段声明行**，不是条目块：

| 口径 | 结果 |
|---|---|
| `基线:` 字段声明行（本 change 采用） | **108** = `touched 23` + `unchanged 72` + `unverifiable 13` — 与自述**逐位吻合** |
| `###` 标题块 | 146 个 `###` 标题，其中含 4 个非条目小节（`基线状态字段怎么读` / `清单 B 的边界` / `对账口径速查` / `本次未做` 等）；此口径下本 change 的计数脚本得 `26/75/17/8`，**同样复现不出 review 的 109** |

即 review 的 109 在两种口径下都不可复现，而字段口径与自述完全一致。
`direct-fixes.md` 侧 review 自己复核为「8 处 `unverifiable`，无误」，与本 change 一致。

**结论**：F-1 不修。原 `基线` 计数保持 `23/72/13`。此条留在 design 里，是为了让下一轮
review 不再把同一处重新报上来，并让「为什么 108 而不是 109」有据可查。

## D2 — `self_check()` 必须报告键集差异，且「仅我方存在」的键必须为空区间

**已核实的事实**（`evidence/verify_artifacts.py` 每次运行都重算，不引用本文件）：

- 原表（仓库外原件）**48** 个 drift 键 / **105** 个区间；
- 本方生成器 **60** 个 drift 键 / **105** 个区间；
- `only-in-mine = 12`，`only-in-original = 0`，`shared = 48`；
- 12 个仅我方存在的键**全部携带空区间列表**，非空的有 **0** 个；
- 48 个共有键的区间**逐键相等**，不匹配 **0** 处，共比较 105 个区间。

**为什么旧自检看不见**：`self_check()` 遍历 `set(o_drift) | set(m_drift)`，对并集中的每个
`path` 取 `want = o_drift.get(path, [])`、`got = m_drift.get(path)`。对仅我方存在且区间为空的
键，`got` 不是 `None`（值是 `[]`），于是走 `elif` 分支比较 `[] != []` ⇒ 恒等 ⇒ 不报问题。
**这正是「零命中与对象不存在不可混读」的同一族失效**：判定逻辑在正确的键上完全正确，
差异只发生在**键集**层面，而键集从未被独立断言。

**修法**：
1. 键集差异**单独计算、单独打印**，三类分别列出（`only-in-original` / `only-in-mine` / `shared`），
   路径清单全量输出（当前 12 条，不截断）。
2. 新增**硬断言**：`only-in-mine` 中的键，若携带**非空**区间 ⇒ 自检报红返回 1。
   空区间键是合法的（`git diff` 会为「有 diff header 但无 hunk」的路径注册键），
   非空区间键则意味着本方多算了东西，必须失败。
3. PASSED 措辞拆成两句，不再用 `files=` 混指区间键数：
   区间相等（`N intervals across M shared keys`）与键集相等（`key sets identical`）分开陈述。
   键集不相等时措辞必须显式写「键集不等（`K` 键仅本方存在，均为空区间）」。

**不做**：不改 `build()` 的区间计算逻辑。已核实 105 个非空区间逐键正确，改它没有依据。

## D3 — 产物文件名必须自带双端点

旧名 `pin_drift_<head[:7]>.json` 里的 `pin_drift` 是**表类型前缀**，`95718cf` 是 head 侧，
读起来像「以 95718cf 为 pin 的漂移表」，而内容 `pin=6593a06`。类型前缀与端点混在一个 token 里，
是歧义的来源。

改为 `drift_<pin[:7]>..<head[:7]>.json` → `drift_6593a06..188b9fb.json`。
文件名读作「从 6593a06 到 188b9fb 的漂移表」，与内容一一对应，无歧义。

**不重命名归档目录里的旧文件**。旧文件本身内容正确，只是名字误导；改名等于原地编辑归档制品。
本 change 在自己的 `evidence/` 下生成正确命名的副本，并在清单 Errata 中登记旧名被取代。

## D4 — `ANNOT` 重复键：合并文本 + AST 自校验（`all()` / 计数断言都不够）

**事实**：`ANNOT` 19 个键，`AC-28` 出现在 L80 与 L90，`AC-29` 出现在 L56 与 L94。
`dict` 字面量保留最后一次，Python 无任何警告。

**为什么不只去重**：两段文本**语义不同**——
- `AC-28` L80 = `[边界保留]`（check-completeness 判 borderline，保留为行动项合理）；
  L90 = `[溯源缺口]`（D1-03 由本条与 AC-04 / AC-15 共同承载，id 未进 `origin_ids`）。
- `AC-29` L56 = `[分桶存疑]`（报告 §11 第 4 条是弃权声明，应落 archive-only）；
  L94 = `[溯源缺口已消 + 位置已更正]`。

只保留其中一段 = 丢一段审计注解。**两段都要保留**，合并进同一条。

**为什么必须加自校验**：合并是一次性动作，防御必须落在生成器里，否则下次有人加注解时
重复键会再次静默发生。可选防御里只有 AST 形态有效——
- 运行时检查 `len(ANNOT) == <硬编码数>`：硬编码数本身就是会漂移的第二真相源；
- 遍历 `ANNOT` 检查内容：不成立，重复键在构造时就已经丢了，后面看不到；
- 改用 list-of-pairs 再折成 dict：可行但改动面大，且不阻止**语义重复**（两段讲同一件事）。

**选定**：`ast.parse(__file__)` → 定位 `ANNOT` 的赋值节点 → 收集 `keys` 节点的 `(value, lineno)`
→ 有重复即 `raise`。它在**字面量层面**捕获，与「后续任何编辑」无关，不依赖任何会漂移的计数。
自校验函数在模块加载时执行 ⇒ 下次有人引入重复键，生成器**加载即失败**，不可能产出静默丢键的表。

## D5 — F-8 / F-9 不在本 change；用户已预先裁决修法，记为待办

用户就范围明确选择「只修 Part 1」。review 第二部分的 F-8 / F-9 属全仓 TDD 缺陷，
必须改三份 spec 与 `tests/`，走独立 change。**用户已预先裁决 F-9 的修法**，在此登记，
使该裁决不因本轮不实施而丢失：

> **两者都做**：用 float64 守护「机器精度恒等」，float32 另设一个可达容差。

F-8（空 cell 不变量在 `tests/test_extraction.py` 无原理级守卫）与 F-9
（`torch.allclose(atol=1e-12)` 被隐式 `rtol=1e-5` 架空）**必须同一 change 内处理**：
F-8 在 F-9 修好之前是无效功（守卫被放宽的容差会同时放行正确值与违规值）。

已核实的前提事实（供后续 change 直接引用，不需重查）：
- `torch.allclose(a, b, atol=1e-12)` 的默认 `rtol=1e-5`，判定式为 `|a−b| ≤ atol + rtol·|b|`；
  在 `|b| ~ 1` 时有效容差约 `1e-5`，比声明宽 **7 个数量级**。float64 实测：漂移
  `1e-12 / 1e-9 / 1e-7 / 1e-6 / 1e-5` 在默认下**全部**返回 `True`，`rtol=0` 下**全部**返回 `False`。
- 全 `tests/` 共 **49** 处 `allclose`，其中写死 `rtol=` 的有 **0** 处，`atol=1e-12` 的有 **4** 处。
- 生产路径（空 cell，`N_e=4, d_c=3`）基线漂移实测 **`7.451e-09`**，已比 spec 声明的 `1e-12`
  超出 **3 个数量级**；`float32` 单精度下 `1e-12` 不可达，这是 spec↔实现的口径矛盾，
  属 CLAUDE.md §6 禁止用 policy 论证关闭的数学语义选择。

**未纳入本 change 的还有** F-4（两份文档模板仍在教废弃值 `33_040`）、F-5
（`decompmoe-skeleton` req-20 的 `abs=1e-4` 与 `wayfinder` req-26 的禁令互斥，已逐字核实为
真矛盾）、F-6 / F-7（`sphere.py` 陈旧 docstring）、C-5（缺参数化配置族测试）。
其中 F-5 阻断「spec 自洽」声明，一并留给后续 change。

## D6 — 为什么本 change 的修正走 Errata 而不是原地编辑归档目录

`CLAUDE.md` §3 规定归档门禁由 `run_gates.py` 统一判定，且「禁止重跑 archive 修复被吞的 anchor」
（`req-gov-10`）——精神是：**已消费的归档制品不可回改**。原地编辑归档目录会：
1. 破坏归档制品不可变约定；
2. 使归档 change 的 `tasks.md` 记录与 `evidence/` 实际内容对不上（tasks 说做了什么，
   evidence 里却多了本 change 才写的脚本）。

既有先例：A-1 / A-2 / A-4 三个 change 的修正都走 `## Errata` 小节。本 change 沿用。

## D7 — 生成器在 **import 时**写文件：一次自伤与它换来的防线

本 change 自己的一个验证脚本，为了检查 `ANNOT` 的键数，**`import` 了
`_gen_listA2.py`**。该模块在**模块级**执行 `io.open(OUT, "w")` 写出，于是
`lists/opsx-changes.md` 被整份重生成覆盖：**1931 行 → 1495 行，4 个 `## Errata` 小节全丢**。

这比「运行生成器会覆盖」更糟：运行生成器是个**显式**动作，import 一个模块去读它的字典
则看起来完全只读。危险在 **import 边界**，不在运行边界。

**恢复**（`evidence/recover_errata_tail.py`）：从 A-6 change 自己的
`evidence/_pre_edit_opsx-changes.md` 快照按**结构边界**（首个 `## Errata` 之前那个 `---`）
取回 369 行尾巴，逐字节校验；再用 A-6 自带的 `write_a6_errata_and_readme.py`（幂等）
补回第 4 个小节。恢复后 A-6 自带验证器 `verify_a6_errata.py` **65/65 全绿**。

**三条防线**（都已实测）：

1. **生成器不再默认写 live 清单。** `OUT` 必须显式给（`argv[1]` 或 `$A6_GEN_OUT`），
   否则写临时文件并打印拼接指引；**显式指向 live 清单直接 `exit 2`**。
   实测：指向 live → exit 2 且 live 文件毫发无损；指向临时文件 → 正常生成。
2. **验证器一律用 `ast` 读生成器，绝不 import。** `verify_artifacts.py` 用 `ast.parse`
   定位 `ANNOT` 字面量与守卫函数；负向探针把守卫函数源码 `exec` 到一个
   `__file__` 指向**损坏副本**的命名空间里，因此真生成器既不被 import 也不被改写。
   （对比：`build_pin_drift.py` 可以安全 import——它的写出在 `main()` 里。这条区别
   本身就是判据：**模块级 `open(..., "w")` 的脚本不能被 import。**）
3. **`lists/opsx-changes.md` 是「生成前缀 + 手写尾巴」的拼接产物**这一性质，
   从只写在 `tasks.md` 的「不做」清单里，提升为写进生成器自己的 docstring 与拒绝逻辑。
   此前它只靠一条 task 文字守着，而 task 文字拦不住一次 import。

**留下的通用教训**：`verify` 类脚本若需要读一个「模块级就写文件」的生成器，
它本身就是破坏源。判据是**模块级有没有 `open(..., "w")`**，而不是「我有没有打算写文件」。

## D8 — 预期内的红：A-6 自带验证器的 `F-errata` 会失败，且必须被钉住

追加本 change 的第 5 个 `## Errata` 小节之后，A-6 change 自带的
`verify_a6_errata.py` 从 **65/65** 变成 **64/65**。失败的是 `F-errata`：

```
FAIL F-errata   all four Errata sections survive (A-1, A-2, A-4, A-6) | sections=5
```

**这不是回归。** 那条检查的期望值写的是「**恰好 4 个**」——它编码的是**写它当时的
状态**，而不是不变量。其它 64 条（A-6 的全部字段级修正）逐条仍绿。

不钉住它的危险很具体：下一个人跑这个验证器看到 1 条红，分不清是预期还是真坏了，
而最顺手的「修法」是**把本 change 的 Errata 删掉**——正好把正确的东西改坏。

所以 `verify_artifacts.py` 里新增 `check_a6_verifier_state()`，断言的是**完整预期**：
总检查数 65、失败数**恰好 1**、且那一条**必须**是 `F-errata`。任何别的失败
（即 A-6 字段修正真的坏了）会立刻报红，与这条已知的陈旧断言区分得开。

这与 D1 是同一族错误的镜像：D1 是「用错的口径数出一个不符的数」，
D8 是「用对的口径数出一个**按设计就会变**的数」。两者都源于**把状态当不变量**。

**不修** A-6 验证器本身——它在归档目录里，修改它等于原地编辑归档制品（见 D6）。
正确的长期修法是在 A-6 的 Errata 口径里把「4 个」改成「≥ 4 个」，但那属于
「决定重做基线口径」那一轮，不在本 change 范围。
