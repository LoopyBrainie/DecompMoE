# Change β design — `pytest.approx(abs=)` 语义勘误

## B1 — 错误为什么能活这么久

`DEFAULT_RELATIVE_TOLERANCE = 1e-6` **确实存在于 pytest 源码**。任何只读常量、不读控制流的人都会得出「`rel` 默认是 `1e-6`」这个结论——而且这个结论**看起来完全可信**：常量名对、值合理、能自洽地推导出 `1.173547` 的 `1.17e-6`，甚至能解释一个真实观察（三个 6dp 字面量里两个 FAIL 一个 PASS 的模式，在两种读法下恰好相同，所以实测无法区分）。

推翻它的是一个**反直觉的「不调用 `max`」的短路分支**。

⇒ 这与本仓 mpmath 三参 `betainc` 返回补值是**同一类失效**：API 里有一个「看起来会生效、实际因条件分支而不生效」的部分。这正是 Change α 的 `req-gov-5` C3 类（默认值当语义）要机器化拦截的对象。

## B2 — 判别方法：必须做行为裁决，不能只读常量

`ApproxScalar.tolerance` 是 property，无法直接观察中间量。所以本 change 的判据是**构造一个让两种读法给出相反结果的输入**：

```
approx(1.0, abs=1e-9)
  读法一（短路）：  容差 1e-9   -> 1.0 + 1e-8  FAIL
  读法二（max）：  容差 1e-6   -> 1.0 + 1e-8  PASS
```

`1.0 + 1e-8` 是关键：它大于 `1e-9` 但远小于 `1e-6`。换一个构造（如 `1.0 + 1e-7`）两种读法都 FAIL，就**没有判别力**——这是本仓反复栽的「守卫没有牙」的形态。

`evidence/_pytest_approx_semantics.py` 同时做源码读取与行为构造，两者一致才落盘。

## B3 — 为什么要标实测环境

`pyproject.toml` 未 pin pytest 版本。本结论**只在 pytest 9.x 成立**：更早的 pytest 版本 `ApproxScalar` 的短路行为可能不同。因此 spec 里的每一处语义陈述都必须带「实测于 pytest 9.1.1」，否则就是一个新的、不知道自己适用范围的绝对断言——正是 α 要消灭的东西。

**可选后续**：把 pytest pin 进 `pyproject.toml`，让这个论断有确定边界。本 change 不做（会牵动依赖解析与 CI）。

## B4 — 规则保留，理由更换

义务 1 的规则「整数闭式必须 bare `==`」**继续有效**，但支撑它的理由必须换掉。正确理由：

> `pytest.approx` 对整数执行的是**浮点比较**，其容差语义由 pytest 版本决定（本仓实测 9.1.1：`abs` 生效时容差恰为 `abs`，否则为 `max(1e-6·|expected|, 1e-12)`）。裸 `==` 在所有量级上给出**可判定且与 pytest 版本无关**的零容差。

这样规则反而更强：它不再依赖「`abs=0` 恰好够严」这个版本相关的事实，而依赖「不经过浮点比较」这个版本无关的事实。
