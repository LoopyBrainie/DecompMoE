# Design

## D1 — AC-43 先改 spec 再改代码，质心作按次调用参数

req-28 要求「扰动**克隆出的那个专家**（质心和/或专家权重）」，而 req-32 声明的
`resurrect_expert(i, j_star, β_per_expert, cfg)` 与 `MVPConfig` 都不携带质心。
**spec 无法同时满足这两条**——这是 spec 自身的内部矛盾，不是代码单方面偏离。

处置顺序有方向性：先提交 req-32 的修订，再提交代码变更。若反过来，就会出现
「代码比 spec 新」的窗口，那正是 AC-75 刚刚关闭的那类缺陷。

质心进 `MVPConfig` 被否：质心是每次复活事件特有的数据（随 `(i, j_star)` 变化），
而 `MVPConfig` 是冻结的配置单例；加一个逐调用变化的字段会破坏它的不变量假设，
并把「配置」与「运行时数据」的边界搅在一起。参数名取 `c_centroids`（矩阵，
非单行）而非问卷草稿里的 `centroid`，因为传的是完整的 `(N_e, d_c)` 矩阵以便按行
寻址——这与仓库内 `sphere` 探针的命名一致。

## D2 — 克隆源取 `j_star`（donor），不是 `i`

用户问卷草稿写的是「从第 i 个专家的质心矩阵取行/列」。实现取 `j_star`，这是对该
草稿的**有意偏离**，理由三条：

- `i` 是待修复的**死专家**，它的质心正是复活要替换的那个退化量。克隆 `i` 等于对
  正在修复的状态做扰动，复活退化成 no-op 换了个随机方向。
- β 双写同样从 `β_per_expert[j_star]` 取**写前**值（`apply_resurrection_beta_decay`
  的既有实现），质心克隆与 β 克隆同源才自洽。
- 审计给的参照量本身就是以 donor 为基准：`E[cos(c_perturbed, c_j*)]`。

因此 Scenario 用 `eps_std → 0` 的极限把这一点变成可执行断言：此时扰动恒为零，
闭式是精确的 `c_perturbed == c_centroids[j_star]`，且**不等于** `c_centroids[i]`。
随机抽样下两行只是「大概率可区分」，极限下才是确定性的。

## D3 — AC-17 删掉替代分支，而不是给它加警告

`mask` 改成必填位置参后，`if mask is None:` 分支在签名层面已不可达。但仅删签名不够：
显式传 `mask=None` 仍会静默走进全批均值路径，正是 AC-17 的缺陷本体。所以两处都改
——签名去默认值，且显式 `None` 抛 `TypeError` 并在消息里指回 req-18。

这不是「为不可能场景写错误处理」（`CLAUDE.md` §2）：`None` 是一条**已被现实调用方
使用过的合法入参**（旧签名允许），迁移期内的调用方会继续传它，删默认值不会拦住它们。

## D4 — 三个钉住退化值的测试改期望值，不改判据

`test_phase_090_ema` / `test_phase_095_to_099_ema_coefficients` /
`test_phase_transition_swaps_rule` 三个测试以 `atol=1e-5` 精确钉住了全批均值广播
的结果。它们的**判据**（EMA 闭式 + 球面重投影 + 两阶段 α 不同）是对的，错的是
`m_i` 的定义。

改法不是把 `X.mean(dim=0)` 换成 driver 内部同样的加权平均——那会让测试变成代码的
复述。改用 one-hot mask，并让期望值走**布尔索引**求均值
（`X[mask[:, e] > 0].mean(dim=0)`），与实现的 `mask.T @ X / n_i` 不共享任何代码
路径。one-hot 是刻意选的：只有它能让期望值用一条与实现无关的写法算出来。

## D5 — `UR` 的跨步聚合：spec 二义，选择并记录

**⚠️ 本节初稿的两条论据之一已被推翻，见文末「D5 更正」。**

**这是本 change 唯一一处口径冲突，且必须写下来。**

req-20 对 `UR` 的全部规范性内容只有一行：
`UR = (1 / N_e) · Σ_{i=1}^{N_e} I[f_i > 0]` over the most recent W = 100 steps，
英文注解「fraction of experts actually selected」。**没有任何闭式 Scenario**
（台账自己也记了「UR 是唯一既无 spec 闭式 Scenario、又无任何数值测试的指标」）。
于是下面两种读法都与文本相容：

- **(A) 窗口内取并集**——「最近 100 步里被选中过的专家占比」。
- **(B) 窗口内逐占比再平均**——`mean_t [(1/N_e)·Σ_i I[f_{t,i} > 0]`。

采纳 **(A)**，依据是 spec 自身的英文注解：`I[f_i > 0]` 是对**专家**的指示函数，
被求和的对象是 `N_e` 个专家而不是 `N_e × T` 个 (专家, 步) 对；配合「actually
selected」（实际被选中过）这一措辞，只有并集读法使整句话自洽。(B) 会让同一句公式在
`T=1` 与 `T>1` 时是两种不同的量纲。

本 change 因此只固定 spec 明确写死的部分：`W = 100` 的截断、单步闭式 `(1/N_e)·Σ`、
以及轴语义（list 索引 / tensor 轴 0 为时间轴）。跨步聚合的判据按 (A) 钉在
`test_ur_reads_axis_0_as_the_time_axis` 里。

**`R_H` 与 `S_load` 的 sliding window 本次不动。** 台账指出两者签名中没有窗口参数，
属实；但 spec 对它们**没有给出任何 W 的数值**（`R_H` 那行只写「over a sliding
window」）。给一个没有指定窗口长度的函数新增窗口参数，是一次未请求的 API 扩张，
且无闭式可钉。按 `CLAUDE.md` §2 记录为明确的 out-of-scope。

### D5 更正（2026-10-02，R1 review 后）

初稿声称「台账为 200 步历史标注的『spec 0.125』只在 (A) 下成立，为 `(B, N_e)` 输入
标注的『spec 0.0625』只在 (B) 下成立」——**这是错的**，已实测推翻：

```
台账自己的 200 步 fixture（窗口内每步恰好 {0,1} 激活）
  并集读法 = 0.125   逐占比均值读法 = 0.125     ← 两者相同，该 fixture 不具区分力
(8, N_e=16) 批量（每步 1 个专家、4 个互异）
  并集 = 0.250       逐占比均值 = 0.0625        ← 只有这个能区分
```

更根本的是，`0.0625` **根本不是 spec 侧 UR 的期望值**。它的出处是
`wayfinder/tickets/A8-2.md:93` 的「接近 1/16 = 0.0625」，而该 ticket 的 UR 是
`f̄_i^(100)`（`:38`）——**per-expert** 的 100 步滑动均值，均匀路由下健康值确实是
1/16。spec req-20 的 UR 是「被选中过的专家占比」，健康值是 1.0。台账把 ticket 的
per-expert 健康值当成了 spec 的判据，属范畴错误。

因此初稿的「两个 spec 值来自两条不同规则」这个框架本身是假的——正确的说法是：
**一个数是真判据（0.125，与 (A) 一致），另一个数根本不是判据。** 结论 (A) 不变，
但它当初被支持的方式有两处错误：一是用一个不具区分力的 fixture 去「证明」区分，
二是把范畴错误当成了对立假说。R1 已把 (A) 写进 req-20 的 Scenario（不再只存在于
测试 docstring），并用**窗口内激活集变化**的 fixture 做真正的区分
（`test_ur_aggregation_is_a_union_not_a_per_step_mean`），同时给 `A8-2.md:38/93`
补了 §8 的 `(historical, …; superseded by …)` 注释。

## D6 — `_UR_WINDOW_STEPS` 刻意不导出

req-1 把公共面钉死在「13 个子模块 `__all__` 的去重并集 = 75，包级含 3 个 dunder =
78」。把窗口常量导出会把并集推到 76，与 C2 刚钉死的数字脱节——正是本 change 要消灭
的那类「两份真相」。故保持私有，并在测试里钉住它既不在 `metrics.__all__` 也不在
`decompmoe.__all__`。

## D7 — 数值闭式必须自己重算，不要从别处搬

AC-17 的回归闭式第一版抄了台账的 per-expert 对照组 `1.8227 / -0.002639`，实测
不符；改为自己重跑后又差一位（`1.419604` vs `1.421196`）——因为抄来的那个数来自
「记录于第 999 步、实为第 1000 次调用」的曲线行。逐字复刻测试循环后得到
`1.421196 / -0.023137`，这才是 999 次调用的真值。

台账自己就注明 AC-17 的坍缩速率「是 harness 特定的」，因此它的对照组数值本就不可
直接搬运。与 A-3 台账记录的问题同源：**派生数字必须自己重数一遍**。

## D8 — 自造缺陷记录

本 change 的实现过程中自己引入并修正了 3 个缺陷，均已在 tasks.md 对应条目标注：

1. 追加测试的生成脚本里 `\\n` 转义被 JSON 解码吃掉一级，在目标文件里留下真实换行
   → `SyntaxError: unterminated string literal`。改为不依赖换行格式的单行匹配。
2. AC-17 回归闭式抄错来源（见 D7）。
3. `test_ur_window_constant_...` 断言包级 `__all__` 为 75，实测 78——C2 钉的是
   「并集 75 / 包级含 3 dunder = 78 / 求和 76 三个数」，我漏了 dunder 这一层。
