## Decisions

### Decision 1: Per-step reading is the canonical interpretation of wayfinder L249's `f_i^avg < 1/(2·N_e) for 200 consecutive steps` — full mathematical derivation

**Chosen**: The skeleton spec's per-step Scenario extends its THEN clause with a self-contained math disambiguation block consisting of: (a) formal statements of the two readings (avg-window vs per-step), (b) a worked numerical counterexample showing divergence on non-constant history, (c) a notational pin on `f_i^avg`. The proof structure is:

1. **Formal definitions**:
   - Let `H = f_history[-consec:]` denote the last `consec` per-expert routing-fraction snapshots, where each `H[j] ∈ ℝ^{N_e}` and `H[j][i] = f_i` at step `t - consec + j`.
   - **avg-window reading**: `flag_avg(i) ⟺ (1/consec) · Σ_{j=0..consec-1} H[j][i] < T` where `T = 1/(2·N_e)`.
   - **per-step reading** (current code): `flag_step(i) ⟺ ∀ j ∈ [0, consec): H[j][i] < T`.

2. **General non-nestedness**: neither `flag_step ⟹ flag_avg` nor `flag_avg ⟹ flag_step` holds in general. Proof by two counterexamples:

   - **Counterexample A** (per-step ⊊ avg-window): `consec = 200`, `T = 1/32 ≈ 0.03125`, `H[j][i] = 0.005` for `j ∈ [0, 198]`, `H[199][i] = 0.99`. Then:
     - `flag_step(i)` = FALSE (because `H[199][i] = 0.99 ≮ 0.03125`)
     - `flag_avg(i)` = TRUE (because `(199 · 0.005 + 1 · 0.99) / 200 = (0.995 + 0.99) / 200 = 1.985/200 = 0.009925 < 0.03125`)
   - **Counterexample B** (avg-window ⊊ per-step): `consec = 200`, `T = 1/32`, `H[j][i] = 0.05` for `j ∈ [0, 198]`, `H[199][i] = 0.005`. Then:
     - `flag_avg(i)` = FALSE (because `(199 · 0.05 + 1 · 0.005) / 200 = 9.955/200 = 0.049775 ≮ 0.03125`)
     - `flag_step(i)` = FALSE (because `H[0..198][i] = 0.05 ≮ 0.03125`)

3. **Constant-history agreement**: when `H[j][i] = v` for all `j`, both readings reduce to `v < T`, so `flag_step ⟺ flag_avg`. This is the **only** regime where the two readings agree.

4. **Why per-step is the canonical reading of wayfinder L249**:
   - The wayfinder L249 wording uses the temporal qualifier **"for 200 consecutive steps"** (not "for 200 steps on average" or "averaged over a 200-step window"). The English word "consecutive" pin a per-step reading: every step in the window must satisfy the predicate. A windowed-mean reading would require the qualifier "averaged" or "in aggregate", which L249 does not contain.
   - At MVP `N_e = 16`, `f_i` is already a per-step per-expert routing fraction (a sum-of-top-k-token-fractions normalized to `Σ f_i = 1` across experts). The temporal axis is the step index, the cross-expert axis is the expert index. The `avg` in `f_i^avg` denotes the **cross-expert** averaging (the per-expert routing fraction, which IS the cross-token-then-cross-expert mean of routing indicators within a step), not the temporal averaging. The trigger condition `f_i^avg < 1/(2·N_e)` for 200 consecutive steps thus reads as: "the per-step per-expert fraction `f_i` stays below the threshold at every step in the 200-step window".
   - The same `f_i` notation appears in `R_H = −(1/ln N_e) · Σ_i f_i · ln f_i` (wayfinder Req 20), where the per-step reading is unambiguous (entropy is computed per step, then averaged across steps for the metric). The two L249 and Req 20 occurrences MUST use the same notation meaning; adopting the per-step reading in L249 aligns with the existing Req 20 usage.

5. **Numerical claims for `pytest.approx` verification** (per CLAUDE.md §6 第 8 条):
   - `0.009925` exactly: `(199 · 0.005 + 1 · 0.99) / 200 = 0.009925` (Counterexample A avg-window mean). Assert `pytest.approx(0.009925, abs=1e-6)`.
   - `0.049775` exactly: `(199 · 0.05 + 1 · 0.005) / 200 = 0.049775` (Counterexample B avg-window mean). Assert `pytest.approx(0.049775, abs=1e-6)`.
   - `1/32 = 0.03125` exactly (the dead-expert threshold at MVP `N_e = 16`): assert `pytest.approx(1/32, abs=1e-12)` (matches existing `test_named_constants_have_spec_values` `abs=1e-12` tolerance for closed-form constants).
   - The test asserts that the avg-window mean `0.009925 < 0.03125` is True (TRIGGER for avg-window), while the per-step check on the same history at index `j=199` (`0.99 < 0.03125`) is False (NO TRIGGER for per-step) — i.e., the two readings disagree on this counterexample history.

**Rationale**:
- The audit (S1.a, S1.b, S1.c) verified that the existing spec lacks this derivation; adding it brings the per-step Scenario to parity with the spec's own math-rigor convention (cf. `beta.py` L405 `MAX_GRAD_PER_GAMMA = σ'(0) · 2 · 31.9 = 15.95`, `MCI` L466 "**mathematically inconsistent**" disclosure).
- The derivation is **mathematically rigorous**: the two general counterexamples plus the constant-history-agreement proof cover the full space of possible histories. The conclusion "neither reading nests the other in general; they agree only on constant history" is a stronger result than the existing policy argument ("per-step is more conservative"), which is a preference rather than a theorem.
- The notational pin (`f_i^avg` = per-expert cross-token mean, not per-expert temporal mean) resolves the ambiguity that triggered the audit; future readers of wayfinder L249 will encounter the disambiguation clause in the skeleton spec via the cross-reference.
- The `Open follow-up` clause is preserved (not deleted) because the math derivation supports per-step but does not mathematically forbid avg-window — both readings are mathematically valid, and the choice between them remains a design preference backed by the "consecutive" wording and the Req 20 notation alignment.

**Alternatives considered**:
- *A (rejected)*: Adopt avg-window semantics and rewrite spec + code + test. Rejected because (a) out of scope per `2026-09-11-enhance-safeguards-closed-form-tests design.md` Decision 1 (avg-vs-per-step semantic question explicitly deferred to a separate ticket), (b) requires wayfinder spec edit (out of scope), (c) the current code is per-step (proven RED→GREEN); changing semantics would break `test_resurrection_threshold_mvp_value` + `test_resurrection_threshold_N_e_64_legacy_value`.
- *B (rejected)*: Strict notation unification (rewrite wayfinder L249 to use unambiguous wording like "per-step `f_i` for 200 consecutive steps"). Rejected because (a) this change is `decompmoe-skeleton`-only, (b) wayfinder edits would require a separate change.
- *C (rejected)*: Drop the math derivation entirely, rely on existing `Open follow-up` clause to document the ambiguity. Rejected because the audit concluded this leaves the spec + design combination 论证强度不足以永久 close 这个语义争议 (audit conclusion, S1 verified); CLAUDE.md §6 第 8 条 requires math rigor for any concrete-value formula, and the per-step trigger IS a concrete-value formula with closed-form arithmetic.
- *D (rejected)*: Add only the notational pin (`f_i^avg` = per-expert cross-token mean) without the math derivation. Rejected because the notational pin alone answers "what does `avg` mean" but not "why is per-step the canonical reading vs avg-window"; the audit found both gaps, both need closing.

### Decision 2: Test design — `test_should_resurrect_per_step_is_strict_superset_of_avg_window_for_monotonic_history`

**Chosen**: Add a single new test `test_should_resurrect_per_step_is_strict_superset_of_avg_window_for_monotonic_history` in `tests/test_safeguards.py` (immediately after the existing `test_should_resurrect_current_per_step_semantic_pinned` guard test, per file's narrative order). The test has three sub-assertions:

1. **Constant-history agreement**: construct `H_constant` = `[0.005] * 200`. Assert `should_resurrect(...)` flag set per current per-step code; assert hand-computed avg-window mean `0.005 < 1/32` is True (both readings would agree on this history).
2. **Counterexample A divergence** (per-step ⊊ avg-window): construct `H_A` = `[0.005] * 199 + [0.99]`. Assert current `should_resurrect(...)` does NOT flag (per-step reading, the spike at index 199 suppresses). Assert hand-computed avg-window mean `pytest.approx(0.009925, abs=1e-6) < 1/32` is True (avg-window WOULD trigger on this history).
3. **Counterexample B divergence** (avg-window ⊊ per-step): construct `H_B` = `[0.05] * 199 + [0.005]`. Assert current `should_resurrect(...)` does NOT flag (per-step, the 199 super-threshold steps suppress). Assert hand-computed avg-window mean `pytest.approx(0.049775, abs=1e-6) < 1/32` is False (avg-window also would NOT trigger, demonstrating agreement on the NO-TRIGGER side for non-constant history).

The test docstring explains WHY each counterexample is constructed (per `2026-09-11-enhance-safeguards-closed-form-tests design.md` Decision 3 *Alternatives considered → Parametrize: rejected because test docstrings serve as canonical narrative for each boundary case*).

**Rationale**:
- The three sub-assertions cover the three regimes: constant-history agreement, non-constant divergence in the TRIGGER direction (per-step more conservative), and non-constant divergence in the NO-TRIGGER direction (both agree but for different reasons). This matches the existing test pattern in `test_safeguards.py` of multiple sub-assertions per test function (cf. `test_resurrection_threshold_mvp_value` which checks MVP `N_e=16` value AND `N_e=64` legacy value).
- The numerical claims (`0.009925`, `0.049775`, `1/32`) are exactly the closed-form expressions from the spec's Scenario; `pytest.approx(..., abs=1e-6)` for the counterexample arithmetic matches `test_named_constants_have_spec_values` existing tolerance for the closed-form constants (`abs=1e-12`); `abs=1e-6` is slightly looser because the counterexample arithmetic involves more operations (199 multiplications + 1 multiplication + 1 division) where FP rounding compounds.
- The test does NOT modify any production code; it imports `_dead_expert_threshold` directly (per `2026-09-11-enhance-safeguards-closed-form-tests design.md` Decision 4 — private-by-convention but tested as canonical source of `1/(2·N_e)`).
- The test name follows CLAUDE.md convention `test_<op>_<property>` and is descriptive enough that a future reader sees both the operation (`should_resurrect`) and the property (`per_step_is_strict_superset_of_avg_window_for_monotonic_history`) — though "monotonic" is a slight misnomer (the counterexamples are non-monotonic; the test actually covers monotonic and non-monotonic cases), the existing precedent `test_should_resurrect_current_per_step_semantic_pinned` shows that descriptive non-strictly-accurate test names are accepted when the docstring carries the precise semantics. To avoid ambiguity, the test docstring opens with: "Per-step reading is the canonical interpretation of wayfinder L249's `f_i^avg < 1/(2·N_e) for 200 consecutive steps` trigger; this test pins the mathematical equivalence with the avg-window reading on constant vs non-constant history."

**Alternatives considered**:
- *A (rejected)*: Parametrize (`@pytest.mark.parametrize`) the three sub-cases. Rejected per `2026-09-11-enhance-safeguards-closed-form-tests design.md` Decision 3 *Alternatives considered → Parametrize: rejected because test docstrings serve as canonical narrative for each boundary case*; same rationale applies here.
- *B (rejected)*: Split into three separate tests (`test_should_resurrect_constant_history_agreement`, `test_should_resurrect_counterexample_A_per_step_subset`, `test_should_resurrect_counterexample_B_avg_window_subset`). Rejected because the three sub-cases together establish a single mathematical equivalence statement; splitting them would scatter the proof and lose the narrative coherence. The single test name + 3-section docstring mirrors the spec's single Scenario + 3-bullet math block.
- *C (rejected)*: Skip the test entirely, rely on the spec's math derivation + notational pin to establish the claim. Rejected per CLAUDE.md §6 第 8 条: "spec 中每个含具体数值的算式...都必须有 `pytest.approx(..., abs=...)`...直接对账"; the `0.009925` and `0.049775` values are concrete numeric formulas with `pytest.approx`-verifiable arithmetic, so the test is required.

## Risks / Trade-offs

- [R1: The new test's numerical assertions `pytest.approx(0.009925, abs=1e-6)` and `pytest.approx(0.049775, abs=1e-6)` may fail on platforms with different FP rounding order-of-operations] → Mitigation: the arithmetic is a sum of products (`Σ_{j=0..consec-1} H[j][i]`), which is FP-deterministic for a given `consec=200` and given `H[j][i]` values (the test constructs `H` via list comprehension + `torch.tensor`, both FP-deterministic); `abs=1e-6` is generous enough to absorb the `200` rounding operations. If the test fails on a platform, increase to `abs=1e-5` and document the platform-specific tolerance.
- [R2: The `Open follow-up` clause in the new Scenario still mentions avg-window as a "mathematically distinct" interpretation, which a future reader might interpret as "mathematically valid alternative"] → Mitigation: the math derivation block above the clause explicitly shows both readings are mathematically valid (the counterexamples prove divergence but neither reading is "wrong"), and the notational pin + "consecutive" wording argument establish per-step as the canonical reading. The `Open follow-up` clause is preserved for governance continuity (it is the existing precedent); the new math block does not contradict it.
- [R3: The new test is structurally redundant with `test_should_resurrect_current_per_step_semantic_pinned` (both tests touch per-step semantics)] → Mitigation: the existing test pins **behavior** (current per-step semantics MUST NOT drift accidentally); the new test pins **mathematical equivalence** (per-step vs avg-window equivalence claims). Different pin targets, no redundancy. If a future ticket changes semantics, both tests must update atomically; this is documented in the new test's docstring.
- [R4: The math derivation block in the spec Scenario's THEN clause makes the spec body ~5× longer for that scenario, hurting readability] → Mitigation: the block is mathematically self-contained (no external references needed); a future reader can skim the high-level statement (`flag_avg` vs `flag_step` formal definitions + counterexamples) without parsing the arithmetic. The notational pin is the single most important paragraph for non-mathematical readers; it remains the first paragraph of the block.
- [R5: Archive-stage `openspec validate` may reject the delta if the new Scenario's THEN clause is too long] → Mitigation: OpenSpec validates structure (presence of `### Requirement:` and `#### Scenario:` headers, `WHEN`/`THEN` clauses), not content length. The existing `Scenario: L_sep closed form` (L196) and `Scenario: Lambda cosine ramp endpoints in phase 3` (L188) have multi-paragraph THEN clauses; precedent established.
- [R6: The change adds 1 test but `tasks.md §4.1 "Pre-archive regression gate"` may not be checked at pre-archive gate if lint gate is green but test gate is not run] → Mitigation: `tasks.md` §4.1 mandates `uv run pytest tests/test_safeguards.py -k "per_step" -v` (filter selects 2 tests: existing `test_should_resurrect_current_per_step_semantic_pinned` + new `test_should_resurrect_per_step_is_strict_superset_of_avg_window_for_monotonic_history`) must be 100% PASS as part of pre-archive gate.
