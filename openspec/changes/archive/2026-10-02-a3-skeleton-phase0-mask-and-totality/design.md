# Design

## D1 — 为什么 req-18 的 Phase 0 义务必须升格为 MUST（而不是只靠 wayfinder 侧收窄）

`wayfinder` req-23 已收窄为 Phase 1–4。如果 skeleton 侧保持原样（「括号里的一句话」），
Phase 0 的范数义务就变成**两边都不管**：wayfinder 说「不适用」，skeleton 说
「是调用方的事」但用的是描述性措辞、无 MUST 关键词、无可验条款。

按 `CLAUDE.md` §6 的「文字断言不构成可验条款」，描述性措辞等于没有条款。所以两侧
必须**成对**落地：wayfinder 划定适用范围，skeleton 承担范围内的义务。少任何一边，
Phase 0 就是契约真空——比原来的「互斥」更难发现，因为不再有任何一条 Requirement
声称自己管它。

## D2 — `mask` 必填条款写「为什么」而不只写「是什么」

条款本身很容易被读成风格偏好。这里写清机制：per-expert masked mean `m_i` 在没有
`mask` 时是**未定义**的，而实现最自然的替代（`X.mean(dim=0)` 广播到所有行）恰好是
AC-17 观测到的 territory collapse——16 个质心被广播成同一个均值，迭代后两两平均
成对 cos → +1.000000。

值得注意的是**测试确实存在但方向错了**：三个测试以 `atol=1e-5` 精确钉住了这个
退化闭式。所以危险不是「没测试」，而是「测试在守护一个 spec 不要求的退化行为」。
条款因此写成「MUST 拒绝而不是替代」，让实现方在编译期而非运行期撞上它。

## D3 — req-1 写死 75 / 78 / 76 三个数，而不是只写「去重」

只写「去重并集」不够：下一位读者仍需自己重跑普查才能知道规模，而**重跑就会
重新踩到求和 vs 并集**。因此三个数一起写：并集 **75**（期望总数）、包级 **78**
（含 3 个 dunder）、求和 **76**（明确标注 MUST NOT 用的那个）。

三个都是**整数闭式**，按 `governance` req-gov-1 必须用 bare `==` 钉、禁止
`pytest.approx(..., abs=0)`（其 `rel=1e-6` 默认值会随量级缩放，违背「钉值零容差」
的意图）。这条留给配套代码 change 的测试。

`flops_per_token` 的绑定优先级写死为 `config`，因为 `metrics` 版自述为
"Mirrors `config.flops_per_token`" 的转发 wrapper——canonical 定义在 `config`。
同时要求 `metrics` 版保持可达，避免「去重」被误读成「删掉其中一个」。

## D4 — X-main38 的修法是加前置条件，而不是改数值容差

req-7 的 `‖C_t‖₂ = 1 (within 1e-5)` 与 req-19 的次单位区矛盾。两条可选修法：
(a) 放宽 req-7 的容差；(b) 给 req-7 的断言加**前置条件**（排除退化区）。

选 (b)。因为 req-19 L465 已用大量篇幅论证 `== 1.0` 只是**显示形式**而非规范等式
——真正的规范主张是维度相关界 `γ_{d_c} ≤ d_c·eps`，且「任何形如 `≤ C·eps` 的固定
常数界对大 `d_c` 都是假的」。若把 1e-5 再放宽一点，既没有依据，也会掩盖真正的
问题：**断言缺的是适用条件，不是精度**。加前置条件后，req-7 与 req-19 使用**同一
个阈值** `ε = 1e-6`，矛盾从「两个不同数字打架」变成「一个阈值的两种正确表述」。

audit 另称「无测试走该分支」，Stage 0 已标记该子项**未复算**（见台账
`X-main38` 的 `verdict_evidence`），故本 change 不宣称已覆盖该分支的测试。

## D5 — 验证时抓到的两个自造缺陷

1. **过计数**：首轮 anchor 复核报 39 个 anchor 且 `req-17`/`req-20` 重复。用
   `git show HEAD:` 对照后确认是**复核脚本自己**的裸正则把反引号内的行内交叉引用
   （"Req 17 (anchored `<a id="req-17"></a>`)"）当成了 anchor 声明。正确规则是
   `^\s*<a id="(req-\d+)"></a>\s*$`（整行即 anchor），此时 23/23、无重复。
2. **凭空发明规则**：复核脚本检查「每个 Requirement 是否都有反链」，报出 18 条
   「缺失」。实际 lint 规则是「**每一条存在的 `**Source:**` 行**必须含反引号包裹的
   capability 反链」——本 spec 只有 4 条 Source 行，4 条全部合规。19 条 Requirement
   根本没有 Source 行，而 lint 并不要求它存在。

**两条都是同一个错误模式**：拿「我以为的规则」去跑，得到的失败项会去指向根本没坏的
东西。修正办法不是改 spec，而是先把 lint 的规则读出来（`lint_no_source_field_drift.py`
docstring 明写四种违规形态），再据此写检查。
